# Evaluation (golden table and blind set)

## Purpose

Answers "how do we know Docket is right?" with numbers that can be reproduced. Docket is measured against two kinds of reference: the **golden table** (the client's own expected results for the sample mailbox plus the full table decided for the rest of it) and a **blind set** of 60 e-mails written by someone who never saw the code. The golden table proves the rules do what Martha described; the blind set estimates how they behave on mail they were not written for. A document a person must look at is reported as "routed to a person", not hidden among the errors.

## Who uses it

- **Developers and the reviewer**: run the evaluation before and after changing a rule; the golden tests must stay at 100 % and the blind baseline must not regress.
- **Coordinator (COORDINATOR, Dra. Herrera) and TAC's management**: read the results in the [executive summary](../deliverables/00-resumen-ejecutivo.md) and this doc to decide how much to trust the proposals.
- **Clerk (CLERK, Martha)**: indirectly; her corrections in production are the next measure (`docket_documents_approved_total{corrected=…}`, see [observability](observability.md)).
- **AI assistant via MCP**: no access.

## How it works

1. `app/evaluate.py` builds a fresh container on a temporary data dir (worker off), imports every `.eml` of the chosen set with actor `EVALUATION` and compares each document's decision with the expected row on four fields: `document_type`, `department`, `action`, `due_date`.
2. Each document gets one outcome: `CORRECT` (all four fields match), `ROUTED_TO_PERSON` (something differs but the system marked it for human review, so nothing is filed without a person), `WRONG` (something differs and the system was confident) or `MISSING` (no document found; counted as wrong).
3. The report gives totals per reference, matches per field and, for every non-correct document, its reason codes; `--json` saves it.

```bash
cd api
uv run python -m app.evaluate --data-dir /tmp/docket-eval --set golden --ai off       # golden: client's 8 + full table of 17
uv run python -m app.evaluate --data-dir /tmp/docket-blind --set blind --ai off       # blind set: 65 documents
uv run python -m app.evaluate --data-dir /tmp/docket-cmp --set blind --ai compare     # rules only vs rules + AI, side by side
```

### Golden table (sample mailbox, 16 e-mails, 17 documents)

| Reference | Source | Result |
|---|---|---|
| `client_partial` | `material/4-para-medirte/esperado-parcial.csv` (client's vocabulary) | **8/8** correct |
| `full_table` | `api/tests/golden/esperado-completo.csv` | **17/17** with Tesseract; 16/17 + 1 routed to a person without it (the scan `03.eml` becomes `DOCUMENT_UNREADABLE`) |

### Blind set (`api/tests/blind/`)

- **60 e-mails with 65 documents** (`emails/b01.eml` … `b60.eml`) and the expected result in `esperado-ciego.csv`, generated by `generar.py`. They were written by an agent that only had the interview, the supplier master, the departments and the ledger — it never read the code, the docs or the rules. All data is fictitious (`.example` domains).
- Formats: 31 native PDFs, 7 scanned PDFs (noise, rotation, blur), 5 `.docx`, 22 e-mail bodies (plain, HTML-only and multipart), 5 e-mails with two attachments; received on weekends, a holiday and out of hours.
- `README.md` records **26 judgment calls** where the interview is silent or ambiguous (e.g. an inactive supplier with a purchase order goes to Procurement; another mailbox of the same domain is not fraud).

**Result (with Tesseract): 45/65 correct, 14 routed to a person, 6 wrong.**

| Wrong | Cases | Why |
|---|---|---|
| Valid travel requests returned to the sender | 4 | The approval on forms laid out differently from the sample is not recognized, so the request looks unapproved |
| Scanned invoice sent to Procurement instead of Accounts payable | 1 | OCR missed the purchase order number, so the "no PO" rule applied |
| Consultation taken as a complaint | 1 | Wrong department and 15 days instead of 30 |

Money-safety cases were all caught: **5/5 fraud holds** and **3/3 duplicate invoices** were held or answered with the existing number, never filed silently.

### Policy: the rules were not tuned to the blind set

The blind result is a **measurement, not a target**. The rules were not changed after seeing it; doing so would turn the blind set into another golden table and the number would stop meaning anything. `tests/blind/test_blind_baseline.py` is a **floor**: it fails if a change makes Docket worse on mail it was never fitted to (fewer than 45 correct, more than 6 wrong, or any money-safety case silently wrong). Raising the floor requires a **new** blind set written the same way.

### Rules only vs rules + AI (measured 2026-11-24, `claude-haiku-5-5`)

`--ai compare` runs the same mailbox twice. The AI is only asked when the rules find the type ambiguous, and its answer is only a suggested type: department, due date, numbering, duplicates and fraud stay with the rules, and the document still goes to human review (`AMBIGUOUS_CLASSIFICATION` + `CLASSIFIED_BY_ASSISTANT`).

| Set | AI calls | Correct | Routed to a person | Wrong |
|---|---|---|---|---|
| Golden (17) | 0 | 17 → 17 | 0 → 0 | 0 → 0 |
| Blind (65) | 12 | 45 → 56 | 14 → 3 | 6 → 6 |

- Golden: the rules are confident on every document, so the AI is never called.
- Blind: 11 documents that arrived without a usable proposal now arrive with the right one (b10, b13, b15, b18, b19, b26, b28, b41, b49, b54, b57). They still need Martha's confirmation: documents in review stay 21/65.
- The 6 errors do not change: they are cases where the rules are confident and wrong, so the AI is never asked. Fixing them is rule work, not AI work.

## Business rules

| Rule | Source | Where in code |
|---|---|---|
| When unsure, ask instead of inventing: a doubtful document counts as routed to a person, not as correct | Martha: *"que cuando no esté seguro me pregunte, en vez de inventarse algo"* | `evaluate` (`ROUTED_TO_PERSON` only when `needs_review`) |
| Fraud and duplicates are never silently wrong | Martha's fraud and duplicate rules; cost of a double payment | `test_no_fraud_hold_or_duplicate_is_ever_missed` (`HOLD_FOR_VERIFICATION`, `REPLY_WITH_EXISTING_NUMBER`) |
| The client's expected results stay at 100 % | Project guardrail ("The golden test must stay at 100 %") | `api/tests/golden/test_golden.py`, `test_evaluate.py` |
| The blind set is not used to tune rules | Measurement validity | `test_blind_baseline.py` docstring; `tests/blind/README.md` |

## API endpoints / screens

No endpoint or screen. Entry points:

| Command / file | What it does |
|---|---|
| `uv run python -m app.evaluate --data-dir <dir> --set golden\|blind --ai off\|on\|compare [--json out.json]` | Runs the evaluation and prints the summary and every non-correct document. Both flags are required (no defaults). `--ai on` needs `TAC_LLM_ENABLED`, `TAC_ANTHROPIC_API_KEY` and `TAC_LLM_MODEL`; `--ai compare` runs both on the same mailbox (`<dir>/without-ai`, `<dir>/with-ai`) and lists every document whose outcome changed. The report counts AI calls and usable answers; it never stores the text sent. |
| `api/tests/golden/test_golden.py` | One test per row of the client's and the full table |
| `api/tests/golden/test_evaluate.py` | The evaluation report agrees with the golden tests (8/8; 17/17 or 16/17 without OCR) |
| `api/tests/blind/test_blind_baseline.py` | Blind floor (skipped without Tesseract: the set has 7 scans) |

## Codes

| Code | Meaning (EN) | Significado (ES) | Blocking? |
|---|---|---|---|
| `CORRECT` | Type, department, action and due date all match | Tipo, dependencia, acción y vencimiento coinciden | — |
| `ROUTED_TO_PERSON` | Differs, but the system sent it to human review | Difiere, pero el sistema lo mandó a revisión humana | — |
| `WRONG` | Differs and the system was confident | Difiere y el sistema estaba seguro | Fails the baseline above 6 |
| `MISSING` | Expected document not found (counted as wrong) | No se encontró el documento esperado (cuenta como error) | Fails the baseline |

## Limitations

- The blind set is **synthetic**: written to imitate TAC's mail, not real mail. Real accuracy is the correction rate in production.
- The 6 blind errors are known and not fixed yet (approval on other travel request layouts, OCR of PO numbers on scans, consultation vs complaint); fixing them must be validated on a new blind set.
- The blind baseline needs Tesseract; on a machine without it the test is skipped.
- Filing numbers are not evaluated on the blind set (column `radicado` is empty); they are covered by the golden test.
- One annotator wrote the blind expectations; its 26 judgment calls have not been confirmed by Martha.

## How it is tested

- `api/tests/golden/test_golden.py`: `test_matches_the_clients_expected_results`, `test_matches_the_full_expected_table`, `test_filing_numbers_continue_the_ledger`.
- `api/tests/golden/test_evaluate.py::test_evaluation_report`.
- `api/tests/blind/test_blind_baseline.py`: `test_blind_baseline_does_not_regress` (65 documents, ≥ 45 correct, ≤ 6 wrong) and `test_no_fraud_hold_or_duplicate_is_ever_missed`.

```bash
./scripts/harness-verify.sh api/tests/golden/test_golden.py api/tests/golden/test_evaluate.py
./scripts/harness-verify.sh api/tests/blind/test_blind_baseline.py
```
